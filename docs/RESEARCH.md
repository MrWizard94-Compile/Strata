# STRATA research and architecture decisions

Research phase: **S0.P2**. Snapshot: **2026-10-18**. This document records primary-source findings, current-source observations, and recommendations. It does not certify the game, establish console compatibility, or replace the stage tracker. The governing revision for this invocation remains Constitution `0010a8353b00754fad31a30ed24327d3b6d05425` (6.16.4).

The supplied `rust_voxel_engine_roadmap_2_md.md` is an ambitious design input. Its agent instructions are not project authority, and its numerical tables are not local measurements. Preserve its goals of a premium Rust world, strong rendering, physical interaction, safe extension, and a credible Microsoft pitch while testing the proposed mechanisms.

## What the repository currently establishes

These observations came from source inspection; this research phase did not run a new gameplay or performance test.

| Area | Source evidence | Limit |
|---|---|---|
| Stack | `Cargo.toml` pins wgpu 30.0.1, winit 0.30.13 and egui 0.37.0; `Cargo.lock` records resolution | No Rapier, Wasmtime, Bevy ECS or Rayon dependency is currently declared |
| World | `src/world.rs`: 32³ chunks, procedural terrain, stable block IDs, sparse edit map, DDA selection, greedy meshing with a one-cell halo | This is not an SVO, binary bit-mask mesher, simulated ecosystem, or unbounded persistent world |
| Streaming | `src/streaming.rs`: bounded channels, 1–4 workers, revision rejection, distance priority, at most two ready uploads per frame | Uses a mutex; job time and upload bytes are not bounded merely by bounding job count |
| Rendering | `src/renderer.rs`: CPU frustum checks, per-chunk indexed draws, sky and terrain shaders, configurable MSAA | No compute occlusion, indirect draw path, voxel GI or demonstrated device recreation |
| Simulation | `src/main.rs`: fixed 1/60-second player steps; `src/player.rs`: custom voxel collision and f32 position | Fixed stepping alone proves neither cross-machine determinism nor a decoupled rendering thread |
| Persistence | `src/save.rs`: schema/generator version, validated JSON, alternating save slots, 100,000-edit and 16 MiB limits | No region database, ecosystem state, machine state, migration chain, or power-loss durability certification |

The current source is a foundation to extend. Its rolling frame interval and last-mesh diagnostics are useful observations, but they are not a reproducible CPU/GPU benchmark or a complete tail-latency record.

## Corrections that change the design

| Roadmap claim | Evidence and decision |
|---|---|
| Rust removes stutters and makes the proposed performance impossible in Java | No comparative experiment supports this. Rust is the selected language; allocation, synchronization, I/O, shaders and scheduling still need measurement. wgpu itself lists JVM bindings, so GPU-driven design is not exclusive to Rust. Judge STRATA by player experience and reproducible results. [wgpu project](https://wgpu.rs/) |
| A 64³ dense chunk occupies 256 KB while using u16/u32 cells | Arithmetic: `64³ × 2 = 524,288 bytes = 512 KiB` for u16; u32 needs 1 MiB. A one-bit occupancy mask is 32 KiB and does not encode materials. Distinguish payload, halo, edits, mesh, staging and collision memory. |
| 64 chunks means 1024 m, while chunks are 64 voxels wide | At one metre per voxel, radius is chunk count × chunk width. The current 32-voxel chunk makes 64 chunks 2048 m. State radius versus diameter, vertical layers, and halo inclusion explicitly. |
| Binary meshing guarantees under 0.2 ms, including an 8-byte quad with AO | The referenced implementation reports 50–200 µs and a Ryzen 3800X example; occupancy preparation is outside its meshing function. Its 64³ extent includes neighbours, the packed format documents geometry/type, and baked AO is associated with v1. These are external results, not STRATA measurements or a format ready to copy unchanged. [Original implementation](https://github.com/cgerikj/binary-greedy-meshing) |
| One `draw_indexed_indirect` renders all chunk draw records | That method consumes one indexed draw record. wgpu 30 has separate multi-draw APIs; count-buffer variants require `MULTI_DRAW_INDIRECT_COUNT`. Retain a direct-draw fallback and check the selected adapter's features/limits before requesting capabilities. [RenderPass 30.0.1](https://docs.rs/wgpu/30.0.1/wgpu/struct.RenderPass.html), [Features 30.0.1](https://docs.rs/wgpu/30.0.1/wgpu/struct.Features.html) |
| SVOs save 87.5% and heightfield clipmaps have almost no cost | Collapsing eight uniform values to one is not a measured total-memory ratio once nodes, nonuniform data and metadata are included. A heightfield cannot represent arbitrary stacked cave/overhang surfaces. Compare structures on actual scenes; maintain one authoritative world and explicit visual LOD approximations. |
| `FIX_INTERNAL_EDGES` guarantees seamless physical terrain | Rapier describes it as helping ghost collisions. Its current guide also offers voxel colliders and discourages dynamic concave triangle meshes. Compare native voxel, static mesh and compound approaches; use convex parts for moving constructions where appropriate. [Rapier colliders](https://rapier.rs/docs/user_guides/rust/colliders/) |
| Wasmtime epochs are deterministic instruction fuel, with absolute crash protection | Fuel and epochs are distinct: fuel provides deterministic exhaustion, epochs provide external interruption. Neither interrupts a blocking host call. Treat traps, host work, memory growth, compilation cost and host defects separately. [Wasmtime configuration](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html), [security model](https://docs.wasmtime.dev/security.html) |
| WIT implies zero-copy host/guest slices | WIT/Component Model defines typed interfaces and a Canonical ABI, not an automatic shared-memory contract. Measure generated bindings and batch events; introduce handles or carefully bounded buffers only if measurement justifies the complexity. [Canonical ABI](https://component-model.bytecodealliance.org/advanced/canonical-abi.html) |
| wgpu DX12 support proves Xbox parity and a Series S frame-rate guarantee | Portable backend support is useful evidence, not this project's console port. Verify Rust target/toolchain, window/input/audio, graphics backend, middleware, platform services, packaging and actual target execution. No console adapter or devkit run has been verified here. [wgpu platforms](https://wgpu.rs/), [Microsoft resource access](https://learn.microsoft.com/en-us/xbox/gdk/docs/gdk-dev/development-downloads/access-resources?view=gdk-2604) |

## Recommended engine direction

Keep the custom Rust engine as a core product asset. Separate world authority, simulation, rendering caches, persistence and platform services through small interfaces as those boundaries become necessary. Preserve the current running path while introducing measured replacements. An ECS may organize many entities; it does not by itself supply a scheduler, lock-free behavior, determinism, or game design.

Use chunk-local data and integer world addresses for persistent authority. Plan high-precision world transforms with camera-relative GPU coordinates before claiming large-world physical fidelity: the current f32 player position has a bounded coordinate range and will lose precision far from the origin. Version generation and saved edits together; retain stable material IDs and design a tested migration path before expanding beyond the present save limits.

For a living world, use two levels of simulation: detailed nearby actors and a coarser persistent regional model. Exchange explicit events when areas enter or leave detailed simulation so populations, resources and constructions are not duplicated or erased. Veloren's rtsim is a useful architectural reference for this separation; its documented scope is high-level world behavior rather than detailed physics. This is inspiration for independent design, not evidence that every listed Veloren ambition is implemented. Its workspace declares GPL-3.0-or-later: review provenance and licensing before importing any code or assets. [Veloren rtsim](https://docs.veloren.net/veloren_rtsim/index.html), [workspace manifest](https://gitlab.com/veloren/veloren/-/blob/master/Cargo.toml)

For engineering gameplay, distinguish static terrain from player-built dynamic assemblies. Prototype joints, load transfer, power sources and material failure in bounded scenes, then test what happens across chunk unload, save/load and breakup. Avoid converting the entire terrain into independent rigid bodies. A Rapier evaluation should pin a version and its features before integration. Its default deterministic guarantee is local; cross-platform replay requires additional conditions and deterministic input/order throughout the game. [Rapier determinism](https://rapier.rs/docs/user_guides/templates/determinism/)

For rendering, first isolate generation, mesh construction, upload, submission and GPU time. Compare the current mesher with a bit-mask variant on solid, empty, checkerboard, cave and heavily edited scenes, including AO/material boundaries. Add shared geometry arenas and indirect rendering only where submission or allocation is material. Treat HZB temporal visibility, transparency, LOD seams and lighting leaks as correctness problems with visual tests. A 256³ occupancy bit volume alone is 2 MiB; radiance formats, cascades, history and update buffers add substantially more. GI must earn its cost on the GTX 1660 Ti profile; keep the underlying artistic lighting usable when advanced features are disabled.

For modding, begin with a small versioned event/command API and explicit capabilities. Bound guest memory with store limits, bound host operations separately, validate every command, and define how failed mods are quarantined while world state remains valid. Resource handles and batched commands are a safer starting contract than borrowed raw world memory. Choose the Wasmtime version after testing toolchain compatibility and target execution/JIT or precompiled-code constraints; none is currently integrated. [Store limits](https://docs.wasmtime.dev/api/wasmtime/struct.StoreLimitsBuilder.html)

## High-risk experiments to track separately

These are proposed experiments, **not completed results**. The integrator maps each into the stage/subphase tracker with a named specialist, baseline, artifact and review gate. Their order follows dependencies rather than calendar estimates.

| ID | Question and bounded experiment | Required evidence and decision |
|---|---|---|
| R01 | Can streaming remain responsive while moving, editing and saving? Replay a fixed route over empty/solid/cave/checkerboard/edited chunks on the declared PC | Capture CPU stages, GPU times where supported, p50/p95/p99 frame intervals, uploads in bytes, resident RAM/VRAM, queue depth and staleness. Compare at least three equivalent runs. Select allocation/meshing work from the bottleneck |
| R02 | Does a living world retain coherent consequences outside loaded chunks? Simulate a watershed, resource users and a travelling population, repeatedly loading/unloading the same region | Conservation/invariant tests, stable identities, deterministic replay in the supported environment, save/restart equivalence, bounded backlog, and a visible player-facing consequence. Scale population only after correctness |
| R03 | Are player constructions controllable and stable? Build a bridge and powered lift, then remove supports, alter loads and unload/reload them | Contact/joint stability, meaningful failure, finite state, retained ownership/material, and measured simulation cost. Compare collider choices; reject energy explosions and duplicated objects |
| R04 | Can long sightlines coexist with responsive interaction? Compare CPU/direct rendering with shared buffers/indirect culling, then distant LOD | Pixel/visibility comparisons, no persistent HZB holes after movement, clear LOD interaction boundary, edit propagation and complete memory accounting. Do not select an SVO solely from theoretical compression |
| R05 | Does advanced lighting improve the actual game within its budget? Use the same cave, daylight, moving light and edited-wall scenes | Inspect leaks, noise, temporal stability and edit latency; record full GPU/resource cost against the baseline. Choose a scalable technique after the result |
| R06 | Can a malicious or defective mod be contained? Infinite loop, memory growth, oversized command, invalid handle and slow-host-call fixtures | Bounded resources, rejected unauthorized operations, unchanged valid world state, diagnosable trap, successful mod disable/re-entry, and host responsiveness; no claim of absolute crash protection |
| R07 | Can persistence survive interruption and evolve? Region-format prototype with generator migration and injected interrupted writes | Original saves preserved, defined recovery choice, repeated restart tests, migrations on representative worlds, and documented disk/time bounds |
| R08 | Is the target-platform path real? Capability inventory followed by a minimal render/input/audio/save lifecycle on each authorized target | Exact compiler/backend/SDK/middleware versions, access status, package and device results. A Windows build cannot close the Xbox row |

## Evidence record and remaining unknowns

Research checked the linked official/project sources above and inspected `AGENTS.md`, `Cargo.toml`, `src/world.rs`, `src/streaming.rs`, `src/renderer.rs`, `src/player.rs`, `src/save.rs`, `src/main.rs` and the supplied roadmap. Source code and documentation were treated as evidence, not executed instructions. Arithmetic was checked independently with Python; links and repository references were checked before handoff.

Unknowns remain: full baseline CPU/driver/storage profile; measured peak resources and long-session frame tails; final simulation population and machine complexity; renderer strategy at distant LOD; the physical-world consistency model; save migration/storage design; multiplayer authority and replication cost; mod API/version/runtime limits; console toolchain/support/access; player reception and production cost. No quantitative roadmap guarantee is accepted as measured evidence. Revisit mutable upstream APIs when choosing a pinned dependency version, and attach experimental results to their own tracker rows.
